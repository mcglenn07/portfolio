RA 9262 Assistant

RAG Web App · AI/LLM · Independent project

Answers questions about the Philippine Anti-VAWC Act (RA 9262) and its 2004 implementing rules, with citations to relevant sections that are filtered against the sections it retrieved. On my 52-question evaluation set, all expected sections were in the top 5 results for 42 of 45 answerable questions, and 7 of 7 out-of-scope questions were refused. Legal information only, not legal advice.

PythonRAGOpenAI APIpgvectorPostgreSQLGradio
Read case study
Problem and users
Understanding RA 9262 often requires reading the Act alongside its implementing rules. I built the assistant to explain the material in plain language, cite relevant sections, and acknowledge when the two documents do not cover a question.
How it works

I converted the source PDF into reviewed Markdown, divided the text into 134 section-based chunks, and embedded them with text-embedding-3-large in pgvector on Supabase.

For each question, the app retrieves the top five sections and adds corresponding sections from a manually verified mapping of 59 pairs of corresponding sections in the Act and its rules. gpt-4.1-mini then generates an answer with citations. A final code check removes citations to sections that were not retrieved.

What I verified
I manually checked all 59 crosswalk pairs and all 52 evaluation questions against the source PDF. A review by a second model identified five issues that I corrected before the final evaluation run.
Design decisions

Chunks follow the documents’ section boundaries and begin with their citation and heading. In comparison runs, adding those prefixes improved top-five retrieval from 39 to 42 of 45 answerable questions.

A cheaper embedding model, smaller chunks, and overlapping chunks produced no measurable difference on this evaluation set. I kept text-embedding-3-large for consistency; the smaller model is a possible cost-saving change.

Evaluation results

The evaluation covered 15 questions about the Act, 12 about the rules, 13 requiring both, five follow-ups, and seven outside the documents’ scope.

  • Retrieval: All expected sections appeared in the top five for 42 of 45 answerable questions, with a mean reciprocal rank of 0.86. Both figures are measured on the ranking before the crosswalk sections are added.
  • Out-of-scope handling: All seven questions outside the documents’ coverage were refused.
  • Incorrect refusals: One of the 45 answerable questions was wrongly refused.

These measure retrieval and refusal behavior on this evaluation set; they do not establish answer accuracy. Answer quality was assessed by an LLM judge, not a lawyer.

Known limits

Most evaluation questions (40 of 52) were drafted by a model from each section’s own text, which may make retrieval easier than it would be for independently written questions.

Documented failures include a follow-up answer that retained unsupported text after its citations were removed, and a filing-deadline question that failed to retrieve the relevant sections. Citation filtering checks whether a section was retrieved; it does not establish that the section supports the answer.

Coverage is limited to the Act and its 2004 implementing rules. Amendments and case law are not included.

WP Diagnostics MCP

MCP Server · Independent project

Gives an AI assistant diagnostic access to a local WordPress installation through seven tools that run WP-CLI commands or read the site's log files. They report plugin and PHP/WordPress information, read the debug log, and run SELECT-only SQL queries. Two tools are built for Gravity Forms support work: one finds entries with error notes, and one reads the latest lines of an add-on's log.

PythonMCPWP-CLIWordPressGravity Forms
Read case study
Problem and users
Gravity Forms support often begins with the same checks: plugin versions, PHP and WordPress configuration, debug logs, add-on logs, and failed notifications or feeds. I built this server so an AI assistant can gather those details directly, to reduce the manual back-and-forth involved in troubleshooting.
The seven tools
  • List installed plugins.
  • Report PHP, WordPress, and WP-CLI information.
  • Read the last lines of debug.log.
  • Run a SQL query through a SELECT-only filter.
  • Find recent Gravity Forms entries with error notes.
  • List available Gravity Forms loggers.
  • Read the last lines of an add-on’s log, by slug.
Design decision

Local by Flywheel assigns each site its own PHP version and MySQL socket. In my setup, a default WP-CLI call failed with a database connection error.

I centralized the configuration in a single run_wp_cli() helper that directs every WP-CLI call to the correct binary and socket. This keeps each tool focused on its diagnostic task, with shared connection settings maintained in one place.

Scope and limits

Built and tested on a local WordPress installation in Local by Flywheel, running Gravity Forms and Gravity PDF. It has not been deployed against a production or remote site.

The SQL tool accepts a single statement beginning with SELECT. This is a basic input filter, not a security boundary, so the tool is intended for use with a local development database.

Resume Autofill for Gravity Forms

WordPress Plugin · AI/LLM · Independent project

A Gravity Forms add-on that autofills a job application form from an uploaded resume before the form is submitted. It extracts the resume text, sends it to OpenAI's Structured Outputs API against a strict JSON schema, and fills the fields configured by the form administrator for the applicant to review and edit.

PHPWordPressGravity FormsOpenAI APIJavaScript
Read case study
Problem and users
Job applicants repeatedly enter information already included in their resumes. This add-on prefills application fields from an uploaded resume so applicants can review and edit their details before submitting. The form administrator chooses the resume upload field and maps the extracted information to the form’s fields.
Design decisions

The model is instructed to return null for missing information rather than infer a value, and to treat resume text as untrusted data and ignore instructions embedded within it.

Applicants must select a consent checkbox before a file is sent for processing, and the API key is stored encrypted. Because parsing happens before Gravity Forms’ spam protection runs, a daily per-IP request limit helps control API costs.

Testing
I tested the complete flow through the applicant-facing form using the live OpenAI API and my own resume PDF. Additional WP-CLI scripts exercised the add-on’s PHP entry points directly.
Known limits

Work history, education, skills, and certifications can only populate Single Line Text fields, with each category condensed into one summary line. The add-on does not support OCR, so applicants using image-only PDFs must enter their details manually.

Resume text is sent to OpenAI, as disclosed in the consent notice. There is no hosted demo; the source code is available on GitHub.

Lecture Notes Pipeline

Local AI Pipeline · AI/LLM · Independent project

Turns lecture recordings and PDFs into structured study notes on an Apple Silicon Mac. It combines extracted slide text with timestamped transcripts and flags slide text that appears not to have been spoken. Files added to a watched folder are processed automatically.

PythonMLXWhisperQwen3.5 VLMPySceneDetectlaunchdClaude Code
Read case study
Problem and users
Lecture slides contain citations, figures, and definitions that lecturers often skip aloud. A transcript alone misses that material. I built this tool for the lectures I study to turn recordings into notes that preserve both spoken explanations and slide content, while keeping the recordings on my Mac.
How it works

A launchd agent watches an Inbox folder and starts a pipeline with each stage running in its own subprocess. The pipeline extracts audio, transcribes it with mlx-whisper and a subject glossary, and detects slides with PySceneDetect using a small proxy video with the webcam overlay masked. It then reads each slide with Qwen3.5-9B through mlx-vlm, aligns speech with slides, uses rapidfuzz to identify content shown but not spoken, and produces one Markdown file per lecture.

A Claude Code slash command merges that file into existing Obsidian notes and flags uncertainties it cannot resolve from the slide frames.

Design decisions

I patched mlx-whisper to apply the subject glossary to every 30-second window, rather than only the first. I selected the OCR model through a scored comparison using 18 slides and 173 manually checked lines, then cross-checked every citation against on-device Apple Vision OCR.

Slides are deduplicated twice: first visually, then by OCR text. The process favors retaining a duplicate over losing a slide. Each stage skips processing when its output already exists, allowing individual stages to rerun independently.

For the merge step, I found Sonnet's output comparable in quality to Opus's in a one-lecture trial, so I used the lower-cost model for the full merge.

What I verified

On a 1-hour, 52-minute recording, I checked every Apple Vision line across all 298 detected scenes against the final slide set and found no missed slides.

Of eight citation-mismatch flags, seven were Apple Vision errors. One caught a real model error: an inferred citation for a line cut off at the edge of the frame.

After each merge batch, a separate script confirmed that all 3,165 slide lines appeared in the notes (using fuzzy string matching) and that the citation numbers in the notes matched the raw extracted files.

Evaluation results

The pipeline processed 45 lectures unattended in about 2 hours and 45 minutes—an average of 3 minutes and 39 seconds per lecture—with no failures. A 1-hour, 52-minute recording at 1782 × 924 resolution took 54–57 minutes, with OCR accounting for 77% of processing time. The 45 batch lectures were shorter, lower-resolution recordings, and OCR time grows with resolution and slide count.

The merge updated 46 existing notes without creating new ones. The pipeline logic is covered by 127 tests. These results reflect my own lecture collection, not a general benchmark.

Known limits

The pipeline is Mac-only because it depends on MLX, Apple Vision, and launchd. OCR accounts for most of the processing time. Detection of content shown but not spoken deliberately favors over-flagging: for a lecturer who skimmed dense slides, it flagged 57% of lines.

Transcription, slide detection, and OCR run locally. The merge step uses Claude Code, so extracted text and any slide frames it checks are sent to Claude. The recordings themselves stay on the Mac. There is no hosted demo.
